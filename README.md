# 麦动平衡 M-Balance · 麦当劳膳食运动平衡专家

> 跑完 5 公里，去麦当劳理直气壮地吃掉一个汉堡——而且不用多花一分钱。

**麦当劳程序员创意开发大赛参赛作品** · 基于麦当劳 MCP Server 开发

---

## 这是什么东西

你有没有过这样的时刻：刚运动完，饿得发慌，特别想吃麦当劳，
但脑子里有个声音在说「白练了」。

**麦动平衡**就是来解决这个纠结的。它不是又一个"帮你省钱"的点餐工具，
而是把**运动科学**接进麦当劳的点餐链路：

```
你练了什么  →  消耗多少卡      →  今天有多少加餐额度
（MET 模型）     （ACSM 公式）      （保守折算 60%）

加餐额度    →  该点什么         →  叠加优惠券  →  核价  →  下单
（kcal 上限）   （营养库挑品）      （四路合券）    （MCP 强制核价）
```

一句话：**把「你今天练了什么」翻译成「你今天该吃什么」，再让这顿便宜点。**

## 为什么值得做

市面上已有的麦当劳工具分两类：算钱的，和推活动的。**没有人管你练完之后该吃什么。**

而「练完能不能吃麦当劳」是真实存在的高频纠结，尤其在健身人群中。
这个问题光靠"看一下热量表"解决不了，因为：

1. 大部分人不知道自己练完到底消耗了多少；
2. 知道消耗之后，不知道该怎么在菜单里花掉这个额度；
3. 想花得划算，还得叠加优惠券——但券的可用范围、门槛、限品规则很绕。

麦动平衡把这三件事串成了一条流水线。

## 核心机制

### 1. 运动 → 加餐额度（本地计算）

采用 ACSM 代谢当量公式：

```
消耗 kcal = MET × 体重(kg) × 时长(h)
```

内置 26 项运动的 MET 表，覆盖跑步、骑行、游泳、力量训练、HIIT、瑜伽、
球类、跳绳、家务、遛狗等，并支持口语化说法（「撸铁」「遛狗」「打羽毛球」都能识别）。

**关键设计：保守折算系数 0.6**

只把消耗的 60% 折算成加餐额度，并且单次上限 700 kcal。这不是技术上的偷懒，
而是刻意的**健康伦理选择**：

- 运动消耗普遍被高估，摄入普遍被低估；
- 运动后食欲上升，很容易吃过量；
- 这个 Skill 的立场是「运动换一顿好吃的」，不是「运动换暴食许可证」。

### 2. 额度最大化组合优化（核心算法）

这是和"省钱助手"最本质的区别：

| | 省钱类工具 | 麦动平衡 |
|---|---|---|
| 目标函数 | `min 实付金额` | `max 额度利用率` |
| 约束 | 预算 | 预算 **且** 热量 ≤ 加餐额度 |
| 结果 | 花最少钱吃一份 | 在预算内把额度吃到最满 |

在双约束下穷举组合，但排序不止看"吃满"：

```
排序键：饱腹合理度 → 额度利用率 → 实付金额
```

**为什么要有「饱腹合理度」**：早期版本只按热量排序，结果最优解是
「麦旋风 + 美式咖啡」——数字上完美，实际上没人拿这个当一餐。
于是引入主食主体判定，`anchor_count ≥ 1` 成为首选方案的底线，
并加了质量兜底：宁可推荐一个汉堡，也不推荐一份孤零零的大薯条。

### 3. 四路合券 + 强制核价

合并「我的券 + 门店券 + 麦麦省可领券」，领券后重查一次券包。
优惠券结算处理了真实业务里最容易算错的三种情况：

- **限品券**：券名写着某个汉堡，但购物车里没有这个汉堡 → 不生效
  （这是真实 bug 的修复记录，见下文「开发过程」）
- **满减门槛**：按券后金额判断，且永远不超过小计
- **兑换券**：挑符合限定条件里原价最高的一件抵扣

下单前**强制**调用 `calculate-price` 核价。本地算得再准也只是估算，
真实结算价必须由服务端说了算——不核价就报价，是最容易翻车的地方。

## 快速开始

### 前置条件

申请麦当劳 MCP Token：https://open.mcd.cn/mcp

### 方式一：离线体验（无需 Token，30 秒上手）

```bash
git clone <本仓库地址>
cd mcd-m-balance

# 用 mock 数据跑通完整链路
python3 scripts/balance_cli.py --demo \
  --activity "跑步 40min, 力量训练 25min" \
  --weight 68 --budget 35
```

输出：

```

  · 蔬菜沙拉　¥9.50　40 kcal
  · 苹果片　¥7.00　35 kcal
  · 零度可乐（中）　¥9.50　0 kcal
```

### 方式二：接入真实麦当劳 MCP

1. 在 WorkBuddy 的【专家·技能·连接器】→【连接器】→【自定义连接器】→【配置 MCP】
   中填入 `mcp-config.example.json` 的内容，把 `${MCD_MCP_TOKEN}` 换成真实 Token。
2. 启用 `mcd-mcp` 连接器。
3. 设置环境变量并运行：

```bash
export MCD_MCP_TOKEN="你的Token"

python3 scripts/balance_cli.py \
  --activity "力量训练 50min" \
  --weight 70 --budget 40 \
  --store-code <门店编码> \
  --json
```

### 方式三：作为 WorkBuddy Skill 使用

把本仓库放入 WorkBuddy 的 skills 目录，或直接把 `SKILL.md` 交给 AI，
然后自然对话即可：

## 开发过程：三个被修掉的真实 bug

这个项目最值得说的不是代码写完了，而是几个**在自测中被抓出来的逻辑漏洞**。
它们都写进了测试用例，防止回归。

### Bug 1：券被用在了没有对应餐品的订单上

初版 `apply_coupon` 对满减券只检查了金额门槛，没检查限定餐品。
结果一张「板烧鸡腿堡立减 6 元」的券，被应用到了一个只有
「可乐 + 沙拉 + 苹果片」的订单上，凭空减了 6 元。

真实点餐里这根本不可能。修复：限品券必须验证购物车真的含有对应餐品。

### Bug 2：健康告警全部丢失

`_build_plan` 生成的告警，在 `optimize` 排序后返回的方案里是空的——
用户界面因此看不到任何健康提示。原因是早期版本把告警算在缓存对象上，
而不是按最终 products 现场生成。修复：告警一律在构造最终 Plan 时实时计算。

### Bug 3：宁可推荐一份薯条，也不推荐一个汉堡

脂肪供能比过滤淘汰了「汉堡 + 薯条」的组合（49% 超标），
结果剩下的最优解是单独一份大薯条——它热量低、没超标，
但它是配菜，不是一餐。

修复：加入质量兜底——当最优方案合理度低于阈值时，
把「单独点一个有主食的餐品」补回候选集。健康约束的目标是筛掉坏方案，
不应该反过来把好方案挤走。

另外还修了两个浮点边界问题（`23g×9/460` 在浮点下等于 `0.4499999...`，
严格 `>` 会漏判"正好踩线"）和一个无限递归（降级分支没有终止条件）。
